## Differs from SDK (#102)

Code reading 2026-10-13 against SDK 4.0.2.55154 PLR `platform/9300/` (`cg/cg.c`, `cg/cg_cache_lock.S`, `cg/cg_mem.c`, `dram_gen4_9300/boot0412/memctl.c`) and `sdk/system/drv/watchdog/watchdog_common.c`. Not measured. Highest risk first.

### 1. DTR latch without the PHY buffer-pointer reset (`clocks fast` tREFI step)

- SDK `_memctl_update_phy_param` (memctl.c:129-156): rewrite `DMCR` (latch), wait 10 clkm, poll `DTR_UP_BUSY_MRS_BUSY` 31, then `DACCR.AC_BPTR_CLEAR` 4 0 → 1. SDK `mc_dram_phy_reset` adds `AC_DYN_BPTR_CLR_EN` 5.
- Ours `clocks.c refi_set()` (runs on every power-up via `clocks fast`, after the CPU change): `DTR0` + `DMCR` rewrite + poll; **no `DACCR` toggle**.
- `ddr_sram.S` is covered: every `dtr_update` path is followed by a `DACCR` clear (after refresh-on, and the second clear after `D`).

### 2. Busy poll right after the `DMCR` write

- SDK waits `_memctl_delay_clkm_cycles(10)` before polling `DMCR` bit 31 (`_periodic_DRAM_refresh`, `_memctl_update_phy_param`).
- Ours polls on the next uncached read (`ddr_sram.S dmcr_idle`, `clocks.c refi_set`): a busy bit that asserts a few clkm late reads 0 and the poll ends before the latch / MRS / refresh toggle has started.

### 3. CPU change: SRAM traffic drain and `PLL_SRAM_CTRL` not done

- SDK `_change_cpu_sram_pll` (cg_cache_lock.S): reads + writes back two words at uncached SRAM `0xbf000000` ("clear ongoing sram traffic") before `SYS_STATUS.cf_ckse_ocp0` = 0; after the relock writes `PLL_SRAM_CTRL` (`sram_pll_sel` 1) **and** `CPU_SRAM_ASY_TIMING` every time.
- Ours `clocks_sram.S`: no SRAM drain; `CPU_SRAM_ASY_TIMING` written since #101; `PLL_SRAM_CTRL` never written (value unchanged as long as the SRAM clock is unchanged).

### 4. `CPU_SRAM_ASY_TIMING` rule hard-codes the SRAM clock

- SDK (cg.c:144-160) compares OCP (= CPU / 2) with `sram_mhz` (250 or 500 = `sram_pll_sel`): `sram_oc0_pulse` = OCP ≤ SRAM; `oc0_sram_pulse` = 0 / 1 / 2 for OCP < SRAM / < 2 x SRAM / else.
- Ours (`clocks.c cpu_set`) uses fixed 250 MHz thresholds. Right only while `PLL_SRAM_CTRL.sram_pll_sel` = 0 (boot `0x85` fits 250 MHz; not read back). Derive from `PLL_SRAM_CTRL` instead.

### 5. `CMU_BC_OC0` / `CMU_BC_LX*` `se_dram` (alias CMUCR SE_DRAM) never rewritten, wrong comparison

- SDK `cg_mem_pll_init` (cg_mem.c:54-55, 60-82): after every MEM PLL change `CMU_BC_OC0.se_dram` = (OCP > MEM ? 0 : 1) with OCP = **CPU / 2**; `CMU_BC_LX0/1/2/LXP.se_dram` = (LX > MEM ? 0 : 1).
- Ours `mem_set` refuses changes where MEM crosses the **full CPU clock** and never writes the bits. With CPU 800: MEM 300 → 650 passes our check but crosses OCP 400 (SDK would set `se_dram` 0 → 1).
- `cpu_set` changes OCP (400 → 500 at 1 GHz) without re-checking `se_dram` / `se_spif` (`se_spif` = OCP > SPIF ? 0 : 1, cg.c `cg_spif_pll_init`). Stock 600 / 650 MHz MEM and 25-153 MHz SPIF cross nothing.

### 6. LX change

- SDK `cg_lx_pll_init`: `lxb_clk_sel` 1, `cmu_divn2_lxb`, `lxb_clk_sel` 0, then `CPU_SRAM_ASY_TIMING.sram_lx_pulse` = (3 x LX ≤ SRAM) and 50 µs. LX window 133-204 MHz.
- Ours `lx_set`: same mux sequence, no `sram_lx_pulse` write (stays 0, correct for any LX ≥ 84 MHz at SRAM 250), no wait; allows codes 2-5 (up to 306 MHz, outside the SDK window).

### 7. Outside the SDK's tables (known, overclock)

- CPU 1000 MHz: SDK `MIN/MAX_CPU_PLL` 400-800 (cg.c `_cg_config_cpu`). MEM above 600: SDK `cg_mem.c` table ends at 600. Self-refresh method (`MPMR0.PM_MODE` 2) has no SDK user.
- Relock choice: SDK derives it from `MODEL_NAME_INFO` bit 4 / [3:0]; ours takes `relock` as an argument (default `PLL_GLB_CTRL0` bit 30 = what the SDK picks for `0x93030001`).

### 8. Minor

- `MCR` prefetch: SDK (`rtk_mem_test/memctl_dram.c`, test code only, never at boot) toggles `ip_ref` then `dp_ref` separately 0 → 1; ours (`clocks fast`, OpenWrt 300-04) toggles both at once.
- Watchdog: SDK `watchdog_enable_set` writes `WDT_CTRL` without then with `WDT_E` and sets `VPE0_GIMR.WDT_PH1TO_IE`; ours (`bootsel.c wdt_on`) one write, IRQ masked (polled U-Boot). `WDT_RESET_MODE` 0 = full chip in both.
- `rtk temp`: prints `THERMAL_METER_RESULT_0 >> 16 & 0xff`; SDK `TEMP_OUT` is 22:16 (bit 23 reserved).
